# Substack DCC collection: 20 workers per shard

**Planned 2026-09-28; revised 2026-09-28. Status: implementation and rollout plan, not a runnable production command.** Ziyang uses Codex on his **local computer** to build and run the project remotely on DCC. The project's DCC assessment tested 20 network threads for one minute on one compute node: 197 HTTP 200, three invite-only HTTP 403, and no 429 across 200 first-page requests with a shared 0.3-second request-start gap. It did not test full-history collection or sustained traffic. The current `team_collection.py` still runs one worker, and batch `2026-09-28-team-v2` pins that collector's file hashes. Do not pass an invented `--workers` option to the current collector or edit the frozen manifest in place.

## Ownership and rollout order

- Keep the two disjoint v2 URL lists and the 2020-01-01 through 2026-09-17 study window: Zherui owns shard 1 (74,127 publications); Ziyang owns shard 2 (74,126). Keep the 93,799 in-frame baseline checkpoints and all recorded shard checkpoints. Zherui's shard-1 pause is still active. Verify Ziyang's current checkpoint state before moving his work; the earlier statement that he had not started was true at cutover, not a standing assumption.
- Target **one 20-thread collector per shard**, each on a DCC CPU compute allocation with one cache, one shard lock, and publication-boundary checkpoints. Twenty workers means concurrent in-flight histories, not 20 Slurm jobs or 20 CPUs. Ziyang implements and pilots shard 2 first. Zherui applies the same reviewed release to shard 1 only after reconciling its checkpoint and resolving the pause; no URL moves between owners.
- Preserve at least **six seconds between request starts per worker**, and treat the additional global request pace as a **shared limit across active shards**. The 0.3-second gate in the short probe was on one node and is not an approved sustained rate per shard. Start the first production-like pilot conservatively with a shared gate of at least 0.6 seconds between request starts, subject to the written Substack permission. A later 0.3-second aggregate gate requires a longer successful pilot and confirmation that the permission covers that rate. If both shards run at once, implement a reliable cross-shard gate/coordinator before starting the second; otherwise run the 20-worker shards at separate times. Two independent 0.3-second gates could produce roughly 400 starts/minute and are outside the tested aggregate pace.

1. Review the written Substack permission for endpoints, aggregate rate, DCC execution location, and retained data. Check DCC appropriate use for this workload. The [DCC policy](https://oit-rc.pages.oit.duke.edu/rcsupportdocs/about/) prohibits unauthorized data mining, directs compute work through Slurm, calls for human oversight of AI tools, and recommends checkpointing for long jobs. Record the allowed aggregate pace; if the permission is narrower than this plan, use the narrower terms.
2. Implement a production parallel mode in the **shared** collector using the existing `parse_publication_history()` and post parser. A single dispatcher assigns each pending URL once. All requests, including pagination and retries, pass through both the six-second per-worker gate and one thread-safe aggregate request-start gate per active operation. Keep checkpoint and status writes serialized; do not share a SQLite connection across unsynchronized threads. Commit one complete publication at a time, preserving recorded successes and failures. Signal/STOP stops new dispatch and lets in-flight publications finish or be retried safely on resume. A 429, 401, challenge, or unexplained 403 stops new requests and writes a durable pause, honoring `Retry-After`; a 403 may be recorded as publication-specific inaccessible only after a reviewed classifier distinguishes the documented invite-only response. Never bypass access restrictions.

Copy the v2 frame, baseline inventory, shard-1/2 assignments, and dates byte-for-byte; pin the new collector and every new runtime module in the new manifest. Each owner migrates only their own shard checkpoint into a separately bound new cache, checking row/payload/error/timestamp equality and preserving `PAUSED.json` and `STOP`; Zherui handles shard 1 locally. Retire an old cache only after its migration succeeds. Refuse a collection launch if an old collector is still live or a destination already has work. The new batch ID, commit SHA, code hashes, and cache paths must be published together in the handoff before Ziyang starts live collection.
4. Keep the existing export/compatibility/merge contract: an export must retain all checkpoint records and checksum manifests, and a complete export must have zero pending assigned publications.
