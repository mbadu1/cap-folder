# Substack DCC 20-worker rollout design

**Updated 2026-09-28.** The parallel runner is implemented in `scripts/substack/parallel_team_collection.py` and has passed offline tests. No live full-history DCC run has been verified. Follow the [runnable command guide](SUBSTACK_PARALLEL_RUNBOOK.md); this page records the design and release gates.

## Assignment and code boundary

- The frozen `2026-09-28-team-v2` lists remain unchanged: Zherui owns shard 1 (74,127 publications), Ziyang owns shard 2 (74,126). The study window remains 2020-01-01 through 2026-09-17. Keep the 93,799 in-frame baseline records and each shard's v2 checkpoint. Zherui's shard-1 `PAUSED.json` remains in force until its access stop is reviewed.
- The original `team_collection.py`, shared history parser, fixture output, v2 manifest, exporter, checker, and merger remain unchanged. The new runner uses one process with up to 20 network threads per shard, the same parser, one SQLite writer, publication-boundary commits, and the same default shard cache. Its own SHA-256 is bound in `parallel_runner.json` so a changed runner cannot silently resume a cache.
- Each worker has at least six seconds between request starts; the runner also enforces at least 0.6 seconds globally **within that process**. The short 20-thread DCC probe saw 197 HTTP 200, three invite-only HTTP 403, and no 429 across 200 first-page requests in about a minute. That does not establish a safe sustained pace. The two shards must run at separate times until a shared cross-shard gate is implemented and verified. The written Substack permission and DCC appropriate-use terms control the allowed rate and location.
- Ziyang uses Codex on his local computer and runs commands in his remote DCC checkout through `ssh dcc-agent '<command>'`, on a CPU Slurm allocation. Twenty threads do not imply 20 CPUs. Keep code, cache, and logs in his designated `/work` space and an independent copy of irreplaceable data. Do not compute on a login node.

## Compatibility and exact alignment

1. Run `check_substack_compatibility.py` on the shared commit. Its 49 offline tests now include parallel scheduling, pause/resume, 20-way checkpointing, exact equality between serial and parallel payloads from the same fixed responses, and the private baseline comparator. The fixed parser fingerprint is still `2987d6b4406fa38ef2ac7700b726f468afff3c576943465d3505a057b16e3ded`.
2. Zherui keeps the 93,799-attempt original baseline local. Its checksummed [40-URL sample](../data/substack_validation/2026-09-28-team-v2/baseline-40-urls.json), selected from the 92,452 successful histories by fixed hash order, is checked into GitHub for both owners. Ziyang rescrapes exactly these URLs with the parallel runner into a disposable DCC cache, then returns its checksummed test export. Zherui runs `validation-compare` locally against the original baseline. It checks the complete normalized payload for every sampled URL, including post order, IDs, dates, text, access values, and hashes. It excludes observation time and SQLite file layout. Only 40 exact matches earn `PASS_EXACT`; any failure, extra/missing record, or changed field is `REVIEW_REQUIRED` and stops the rollout for review. The test records never enter either production cache or final merge.
3. A live source may have changed after Zherui's original scrape. On `REVIEW_REQUIRED`, retain both records and inspect the current source response. A same-response replay through both collectors can distinguish source drift from a collector discrepancy. Do not rewrite the historical reference to force a pass. Ziyang needs only the URL list, never Zherui's shard-1 or baseline database.
4. Run a five-publication shard-2 pilot, then a bounded 20-worker full-history pilot with request-start times, HTTP statuses, throughput, memory, checkpoint growth, and stop-state review. A 401/429 or open circuit pauses the run; HTTP 403s without rate-limit evidence are retained as failures and skipped, as specified in the runbook; retain `PAUSED.json` until diagnosed. Continue the same cache only after the gates and permission terms are satisfied. A final export needs the existing compatibility check with zero pending publications; recorded failures are reported separately.
5. Follow the [monitoring procedure](SUBSTACK_PARALLEL_RUNBOOK.md#monitor-the-active-run): observe the validation test about once per minute, and monitor authorized production every ten minutes. Bind checks to the actual cache, process, node and Slurm job; check requests as well as publication commits. Ziyang must configure and verify his own persistent monitor before leaving production unattended. Repository checkout alone does not activate monitoring. Monitoring is read-only and does not authorize restarts or production launch.

The 40-history comparison samples the earlier baseline directly. Both production shards are disjoint from the baseline, so their assigned URLs have no older local row for one-to-one comparison. The sample is an alignment check, not a proof that every new publication equals a historical one. The offline same-input test establishes parser/output parity, and every production export is checked for schema and integrity before the baseline-plus-two-shard merge.
