# Substack DCC collection: 20 workers per shard

**Planned 2026-09-28. Status: implementation and rollout plan, not a runnable production command.** The project's DCC assessment tested 20 network threads for one minute on one compute node: 197 HTTP 200, three invite-only HTTP 403, and no 429 across 200 first-page requests with a shared 0.3-second request-start gap. It did not test full-history collection or sustained traffic. The current `team_collection.py` still runs one worker, and batch `2026-09-28-team-v2` pins that collector's file hashes. Do not pass an invented `--workers` option to the current collector or edit the frozen manifest in place.

## Ownership and rollout order

- Keep the two disjoint v2 URL lists and the 2020-01-01 through 2026-09-17 study window: Zherui owns shard 1 (74,127 publications); Ziyang owns shard 2 (74,126). Keep the 93,799 in-frame baseline checkpoints and all recorded shard checkpoints. Zherui's shard-1 pause is still active. Verify Ziyang's current checkpoint state before moving his work; the earlier statement that he had not started was true at cutover, not a standing assumption.
- Target **one 20-thread collector per shard**, each on a DCC CPU compute allocation with one cache, one shard lock, and publication-boundary checkpoints. Twenty workers means concurrent in-flight histories, not 20 Slurm jobs or 20 CPUs. Ziyang implements and pilots shard 2 first. Zherui applies the same reviewed release to shard 1 only after reconciling its checkpoint and resolving the pause; no URL moves between owners.
- Preserve at least **six seconds between request starts per worker**, and treat the additional global request pace as a **shared limit across active shards**. The 0.3-second gate in the short probe was on one node and is not an approved sustained rate per shard. Start the first production-like pilot conservatively with a shared gate of at least 0.6 seconds between request starts, subject to the written Substack permission. A later 0.3-second aggregate gate requires a longer successful pilot and confirmation that the permission covers that rate. If both shards run at once, implement a reliable cross-shard gate/coordinator before starting the second; otherwise run the 20-worker shards at separate times. Two independent 0.3-second gates could produce roughly 400 starts/minute and are outside the tested aggregate pace.

## Release required before DCC collection

1. Review the written Substack permission for endpoints, aggregate rate, DCC execution location, and retained data. Check DCC appropriate use for this workload. The [DCC policy](https://oit-rc.pages.oit.duke.edu/rcsupportdocs/about/) prohibits unauthorized data mining, directs compute work through Slurm, calls for human oversight of AI tools, and recommends checkpointing for long jobs. Record the allowed aggregate pace; if the permission is narrower than this plan, use the narrower terms.
2. Implement a production parallel mode in the **shared** collector using the existing `parse_publication_history()` and post parser. A single dispatcher assigns each pending URL once. All requests, including pagination and retries, pass through both the six-second per-worker gate and one thread-safe aggregate request-start gate per active operation. Keep checkpoint and status writes serialized; do not share a SQLite connection across unsynchronized threads. Commit one complete publication at a time, preserving recorded successes and failures. Signal/STOP stops new dispatch and lets in-flight publications finish or be retried safely on resume. A 429, 401, challenge, or unexplained 403 stops new requests and writes a durable pause, honoring `Retry-After`; a 403 may be recorded as publication-specific inaccessible only after a reviewed classifier distinguishes the documented invite-only response. Never bypass access restrictions.
3. Create a **new versioned batch/release** for the parallel collector. Copy the v2 frame, baseline inventory, shard-1/2 assignments, and dates byte-for-byte; pin the new collector and every new runtime module in the new manifest. Verify exact URL equality and disjointness against v2. Do not mutate the v2 manifest or its caches. Migrate existing shard checkpoints into separately bound new caches with row/payload/error/timestamp equality checks, preserving `PAUSED.json` and `STOP`. Retire old caches only after successful migration. Refuse a collection launch if an old collector is still live or either destination already has work. The new batch ID, commit SHA, code hashes, and cache paths must be published together in the handoff before Ziyang starts live collection.
4. Keep the existing export/compatibility/merge contract: an export must retain all checkpoint records and checksum manifests, and a complete export must have zero pending assigned publications. Update the compatibility checker and fixture manifest for the new batch while keeping parser golden outputs unchanged if parser behavior is unchanged. Merge only a baseline and both exports from the **same** new batch. Resolve creator IDs and sample globally after merge.

| DCC preflight | From Ziyang's own checkout, verify the exact release commit, batch/assignment/code hashes, Python, effective CPU/memory/walltime/partition, available space, private output location, and exclusive shard-2 cache. | Five-publication parser pilot | On the new shard-2 cache, collect five assigned publications and check bodies, dates, errors, status, and a partial export (`PASS_PARTIAL`). Preserve the checkpoint. This checks real parsing but is too small to validate 20-way concurrency. |
| Bounded 20-worker pilot | Continue the **same** cache through at least 20 pending publications, then a measured 30–60-minute full-history run at the permission-compliant aggregate gate. Capture request-start timestamps, HTTP statuses, `Retry-After`, throughput, memory, CPU, database integrity, bytes stored, and committed publication counts. Stop at any unexplained access/rate event, challenge, quota issue, or loss of checkpoint progress. A clean first-page probe alone does not pass this gate. |
| Sustained shard-2 run | Only after the earlier gates pass, resume the same cache in bounded, restartable Slurm allocations. Check committed counts and logs, not just PID/job state. If both shards overlap, verify the cross-shard aggregate gate with telemetry before overlap. Final merge must reconcile all 242,052 in-frame publications and preserve all failures. |

For DCC runs, use the existing `dcc-agent` CPU route and verify the effective Slurm allocation. Prefer short checkpointed allocations over assuming a two-day walltime or permanent proxy session. Do not `scancel` agent jobs to force a resource change. A requested resource change only affects a future allocation. Register an actual production job ID and remote checkpoint/log paths with the prepared monitor only after launch; a monitor registration is not evidence that collection began.
